# 对客收单生产化整改方案

> 基于 2026-09-04 代码审查。范围为收单（PAYIN）对客开放；出款保持当前失败关闭状态，不纳入本方案。

## 1. 结论与目标

当前系统已具备订单、路由与费率快照、Outbox、资金幂等入账、退款和运营处置的基础能力，但只适合内部模拟或运营原型，不能直接对商户开放。

本方案的上线目标是：商户只能操作自己的订单；支付成功只能来自已验真的真实渠道；通知可由商户验真且不会访问内网；过期、重复和异常支付可恢复；在压测证据支持前不承诺万级 TPS。

## 2. 整改优先级

| 优先级 | 上线结论 | 整改项 |
| --- | --- | --- |
| P0 | 未完成不得开放任何真实商户或资金账户 | 商户认证与订单归属、移除公网模拟控制、真实渠道成功证据 |
| P1 | 未完成不得进行生产收款 | 回调 URL 防 SSRF、商户通知签名、订单过期控制、响应数据最小化 |
| P2 | 生产灰度前完成 | 标准收银台交付、渠道调用可靠性、容量治理、监控告警和演练 |

## 3. P0：安全与资金正确性

### 3.1 建立商户 API 身份边界

**现状**：`/api/v1/payments/orders` 仅由请求体中的 `merchantId` 定位商户，接口没有认证、请求签名、重放保护和订单归属检查。

**改造**：

1. 新增商户 API 凭证模型，至少包含 `merchantId`、`keyId`、密钥密文/密钥引用、状态、有效期、IP 白名单、轮换时间和审计信息。
2. 在网关或 Trade Service 的对客过滤器中认证 `X-Merchant-Key-Id`、时间戳、nonce 和请求签名。签名原文必须定义为 HTTP 方法、路径、规范化 query、时间戳、nonce 与原始 body 的摘要；使用 HMAC-SHA256 或已确定的非对称签名协议。
3. 从认证上下文获取 `merchantId`，禁止从对客 body 信任或接受该字段。将其从创建订单 DTO 中移除。
4. 对查询、状态查询、取消、订单处理 查询/取消/重试、退款创建/查询/执行均执行订单所属商户校验。未知订单和非本商户订单统一返回不可枚举的错误。
5. nonce 按 `merchantId + keyId + nonce` 去重并设置合理有效期；校验时钟偏差，记录认证失败和签名失败审计。
6. 管理端仍使用既有 JWT/RBAC；渠道回调单独使用渠道验签，不复用商户认证。

**涉及位置**：`trade-service/.../controller/OrderController.java`、`RefundController.java`、`gateway-service/.../filter`、商户凭证及平台内部快照接口。

**验收**：跨商户创建、查询、取消、退款和 订单处理 操作均被拒绝；篡改 body、路径、时间戳或 nonce 的请求被拒绝；同 nonce 重放被拒绝；密钥轮换后旧密钥按策略失效。

### 3.2 隔离模拟渠道与测试控制

**现状**：公网 订单处理 创建接口暴露 `behavior`，`SIMULATED` 渠道可返回成功，随后触发 `PAYMENT_SUCCEEDED` 和资金入账。

**改造**：

1. 从所有对客和管理生产接口移除 `behavior` 参数；测试行为只允许在测试 profile 或测试替身中使用。
2. `SIMULATED` 渠道仅允许 `local/test` profile 注册，生产启动时校验并拒绝模拟 provider、生效的模拟渠道或模拟签名密钥。
3. Fund Service 只消费由可信 Trade Service 发布、符合稳定事件契约的 PAYIN 成功事件；事件应显式携带 `orderType=PAYIN`，消费端拒绝其他类型。
4. 真实渠道接入前，不允许任何真实商户或真实账务账户使用该流程。

**验收**：生产配置包含 `SIMULATED` 时启动失败；公网请求无法控制支付状态；只有真实渠道验签成功且订单/订单处理 状态可转换时，才能发布成功事件和入账。

### 3.3 真实渠道接入准入

每个渠道必须先形成供应商合同表并经联调验收：创建/查询/取消/退款 URL、方法、字段、金额单位和精度、超时、签名规范、回调字段、成功确认语、错误码、重试和幂等规则。不得猜测或用通用字段替代供应商规则。

渠道适配器必须完成：请求签名、响应校验、回调验签、回调重放防护、状态映射、支付链接/二维码/收款账户交付、主动查询与对账字段保存。回调验签必须在状态变更前完成，且签名字段使用原始值和供应商规定编码。

## 4. P1：对客安全与订单生命周期

### 4.1 回调 URL 防 SSRF

**现状**：仅允许绝对 HTTP(S) URL，通知消费者会直接发起 HTTP 请求。

**改造**：

1. 只允许 HTTPS，HTTP 仅可在本地测试 profile 启用。
2. DNS 解析后拒绝 loopback、link-local、RFC1918 私网、CGNAT、IPv6 本地/唯一本地、云元数据和保留地址；每次重定向均重新校验，默认禁止重定向。
3. 通过受限 egress 网络或专用通知代理发送，不允许通知服务访问内部网段、控制面和数据库网络。
4. 设置请求/响应大小上限、连接/读取超时、域名/IP 限速和审计；禁止回传敏感响应正文。

### 4.2 商户异步通知契约

通知 payload 应只包含业务必要字段：`eventId`、`eventType`、`occurredAt`、`orderId`、`merchantOrderNo`、`status`、`amount`、`currency`、`paidAt`。不发送渠道密钥、路由/费率快照、客户引用或内部错误。

增加 `X-Payment-Key-Id`、`X-Payment-Timestamp`、`X-Payment-Nonce`、`X-Payment-Signature`。商户按固定签名原文验签，服务端使用商户通知密钥签名并支持密钥版本轮换。商户返回任意 2xx 代表接收成功；同一 `eventId` 可重复投递，商户按事件 ID 幂等处理。

投递策略调整为异步指数退避和可配置最大时长，避免 RocketMQ 消费线程内 `Thread.sleep` 阻塞；最终失败进入死信/待处理队列，支持带权限和审计的人工重投。

### 4.3 订单过期与状态一致性

1. 创建订单时校验 `expireAt` 必须晚于当前时间，并限制最小/最大有效期。
2. 创建 订单处理、重试 订单处理、渠道回调成功、主动查询转成功之前均校验订单未过期；过期订单不得进入成功或入账。
3. 增加订单过期任务，原子地将 `CREATED/PAYING/UNKNOWN` 转为 `EXPIRED`。状态机、数据表、后台筛选和通知契约同步支持该状态。
4. 若渠道在本地过期后反馈已成功，进入人工对账/异常处理队列，不自动入账；以渠道规则、清算结果和运营审批决定补单或退款。

### 4.4 收敛对客响应

建立独立的商户 DTO，只返回订单号、商户订单号、金额、币种、订单状态、过期时间、支付交付信息和必要的失败码。不得返回 `paymentToken`、请求/响应原文、渠道配置、费率快照、回调地址、客户引用、内部异常和通知投递错误。

运营详情仍可查看经过脱敏的快照，但必须保留既有 RBAC、数据范围和审计。

## 5. P2：完整支付体验与可靠性

### 5.1 标准收单交互

将“创建订单”和“创建支付 订单处理”设计为明确契约：对客创建成功后返回渠道支付 URL、二维码内容、表单参数或支付令牌之一，并说明其有效期。支付交付信息必须源自已持久化的渠道结果，不能使用模拟 token。

是否自动创建 订单处理 应由产品接口统一决定：

- 托管收银台：创建订单同步返回支付交付信息；
- 服务端支付：创建订单后由受保护的商户接口创建 订单处理；
- 运营补偿：保留在管理端，且不能暴露测试控制。

### 5.2 外部调用与一致性

不要在数据库事务中持有渠道网络调用。推荐流程为：持久化 `订单处理=CREATED` 和请求幂等号 -> 提交事务 -> 调用渠道 -> 条件更新 订单处理 -> 同事务更新订单与写入 Outbox。调用超时必须进入 `UNKNOWN/PROCESSING`，由主动查询和渠道回调最终收敛。

为渠道请求设置连接、读取、整体超时、熔断、隔离舱和限流；按渠道请求号保证外部幂等。对于“渠道受理但本地未更新”的失败，通过查询任务恢复，而非再次创建扣款。

### 5.3 性能与容量

新订单目前同步依赖平台配置快照服务。上线前应对已发布配置做版本化本地缓存，配置发布事件驱动失效；设置超时、熔断与降级规则，避免平台短暂故障放大为订单不可用。

万级 TPS 的验收应覆盖网关、Trade、Platform、MySQL、RocketMQ、Fund、渠道连接池和通知服务，至少测量：P95/P99 延迟、成功率、数据库连接与锁等待、消息积压、CPU/GC、缓存命中率、渠道超时和错误预算。只有端到端压测与故障演练达到目标后，才能声明对应容量。

### 5.4 可观测性与运营

建立以 `requestId`、`traceId`、`orderId`、`orderId`、`channelOrderId` 关联的全链路追踪。增加订单成功率、UNKNOWN 时长、主动查询成功率、回调验签失败、重复回调、Outbox DEAD、通知失败、账务入账失败、对账差异和跨服务延迟告警。

运行手册需覆盖渠道不可用、回调堆积、消息积压、账务消费失败、通知失败、订单长时间 UNKNOWN、渠道账单差异和密钥泄露轮换。资金类人工操作必须有权限、双人复核、原因和审计。

## 6. 实施顺序

1. 冻结真实商户入口与真实资金入账，生产环境禁用 `SIMULATED`。
2. 完成 P0 商户认证、归属校验、模拟控制隔离与 Fund 事件类型校验。
3. 完成 P1 SSRF 防护、通知签名、过期状态机和商户响应脱敏。
4. 选择首个真实渠道，按供应商文档完成适配器、沙箱和生产联调。
5. 完成支付交付、外部调用拆分、配置缓存和异常恢复。
6. 进行安全测试、集成测试、故障演练和容量压测；小流量灰度后再扩大商户范围。

## 7. 测试与上线门禁

必须新增并通过以下测试：

- 商户认证、签名篡改、时间偏差、nonce 重放、密钥轮换、IP 白名单和跨商户越权。
- 订单/订单处理 并发、幂等键冲突、渠道超时、重复回调、乱序回调、终态保护、过期订单和补偿查询。
- 回调 URL 的内网、IPv6、重定向、DNS 重绑定和云元数据拦截。
- 商户通知签名、重复投递、非 2xx 重试、死信和人工重投审计。
- 真实渠道的签名向量、金额精度、状态映射、退款和渠道账单对账。
- 全链路压测、消息重复投递、数据库故障、平台配置不可用和渠道不可用演练。

上线前由安全、渠道、资金、运维共同签署验收。当前单元测试通过只能证明部分领域逻辑可编译运行，不能替代以上生产门禁。
